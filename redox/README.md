# elanfp для Redox OS

Тот же драйвер, что и на Linux: протокол сенсора (`core`), касания, регистрация, проверка, хранилище и служба с правами
доступа (`engine`) общие. Здесь только то, что относится к Redox:

| файл | что делает |
|---|---|
| `src/usb.rs` | транспорт через `xhcid_interface`: три конечные точки сенсора, передачи не длиннее 65536 байт |
| `src/scheme.rs` | служба-схема `fingerprint.elanfp` на `redox-scheme` |
| `src/keys.rs` | ключ шаблонов в `/var/lib/elanfp/master.key` |
| `src/bin/elanfpd.rs` | драйвер, который запускает `xhcid` |
| `src/bin/elanfp.rs` | клиент: `enroll`, `verify`, `list`, `delete`, `unlock` |
| `dist/xhcid.d/elanfp.toml` | правило сопоставления для `xhcid` |
| `dist/recipe.toml` | рецепт для cookbook |

## Как это устроено
```
xhcid ── /usr/lib/xhcid.d/elanfp.toml ──> /usr/lib/drivers/elanfpd <схема> <порт> <интерфейс>
                                                │
                              /scheme/fingerprint.elanfp/request  <── elanfp, будущие клиенты
                                                │
                                   /var/lib/elanfp (0700 root)
```
- `xhcid` находит интерфейс `04f3:0c4b` (класс 255/0/0) и запускает `elanfpd`. До первой команды служба сверяет
  раскладку USB (одна конфигурация, один интерфейс, пять конечных точек в известном порядке), затем по шагам — прошивку,
  поколение и размер сенсора: на первом же расхождении она останавливается, не отправляя следующих команд.
  Только после этого регистрируется схема.
- Клиент открывает `/scheme/fingerprint.elanfp/request`, отправляет строку запроса (можно по частям, до перевода
  строки) и читает ответы — тот же текстовый протокол, что на Linux идёт через unix-сокет (`elanfp-ipc`). Ответа можно
  ждать через `poll`. Запрос, отправленный без ожидания ответа, всё равно выполняется, если ему не нужен сенсор.
- Кто спрашивает, служба узнаёт от ядра (`CallerCtx.uid`) в момент открытия; писать в чужой открытый дескриптор от
  другого пользователя нельзя. Правила те же, что на Linux: регистрация, удаление и снятие блокировки — только root,
  проверка и список — свои пальцы или root; пять неудач подряд — блокировка, каждая следующая вдвое дольше.
- Служба однопоточная и нигде не спит: паузы и интервалы опроса — это ожидание событий схемы с таймером, поэтому
  остальные запросы обслуживаются и во время операции с сенсором. Второй запрос к сенсору получает `BUSY` (а второй
  запрос на того же пользователя ещё и отменяет ожидающий), список и удаление отвечают сразу, закрытый клиент
  освобождает сенсор.
- Имя схемы, оставшееся от умершей службы, новая служба забирает себе; у живой службы имя не отбирается.
- Дескрипторы, которыми никто не пользуется 10 секунд, уступают место новым, когда свободные кончились.
- Запрос с `fmt=keys` получает ответы ключами сообщений вместо готового текста — для программ, а не для людей.

## Ограничения USB-стека Redox и как мы с ними живём
`xhcid` обрабатывает запросы по одному и не умеет ни таймаут, ни отмену передачи: чтение, на которое устройство не
ответило, останавливает весь контроллер. Поэтому транспорт объявляет `Waiting::Unbounded`, а общий движок сам выбирает
для такого транспорта опрос кадрами: каждый обмен — «запрос → гарантированный ответ», палец ищется по покрытию кадра раз
в 120 мс, дедлайны считаются своими часами. Команды сенсора «ждать палец» (`40 3f`, `40 3e`) на Redox не используются
вовсе. Если сенсор перестанет отвечать на обычный запрос, служба зависнет вместе с `xhcid` — это ограничение системы,
в драйвере оно не обходится.

Ещё пять вещей, найденных на практике:
- После любой неудавшейся передачи `xhcid` оставляет конечную точку нерабочей до перезагрузки. Служба после первой
  ошибки передачи больше не шлёт команд и отвечает на все запросы понятной ошибкой.
- Запрос состояния конечной точки (`XhciEndpHandle::status`) на этом устройстве не возвращается; служба его не делает.
- `std::thread::sleep` в потоке, обслуживающем схему, может не проснуться. Поэтому ожидание сделано через таймер
  `/scheme/time` в общей очереди событий, как в `ptyd`.
- Каждая запись срока в таймер `/scheme/time` добавляет своё событие, прежнее не отменяется. Поэтому на одну паузу
  таймер взводится один раз: иначе чужие запросы во время паузы копят просроченные события, и служба крутится вхолостую.
- Имя схемы может снять любой процесс, оставшийся в пространстве имён службы с правом удаления: драйвер этому помешать
  не может. Зарегистрировать схему вместо службы обычный пользователь не может — это проверено.

## Сборка и проверка
Нужен `redoxer` (`cargo install redoxer --locked && redoxer toolchain`).

| команда | что проверяет |
|---|---|
| `cd redox && redoxer build --release --locked` | сборка под `x86_64-unknown-redox` |
| `scripts/redox-test.sh` | тесты `core`, `engine`, `ipc` и тесты схемы с имитатором сенсора — внутри Redox в QEMU; тесты схемы идут дважды за одну загрузку, второй раз — на именах, оставшихся от первого |
| `scripts/redox-hw.sh` | настоящий сканер, проброшенный в Redox: регистрация и проверка пальца вживую (пользователь 1000) |
| `scripts/redox-hw.sh "elanfp list --uid 1000"` | то же с произвольной командой вместо регистрации |

`scripts/redox-hw.sh` требует доступа к USB-устройству (правило `scripts/70-redox-passthrough.rules`, только для
разработки). Пока виртуальная машина работает, сканер недоступен Linux.

Что проверено на 2026-11-19 (base `8f576d27`, redoxer 0.2.63):
- тесты внутри Redox: `core` 15, `engine` 94, `ipc` 12, схема 14 (и ещё раз 14 в той же загрузке) — все проходят;
- настоящий сканер в QEMU: `xhcid` запускает службу по `elanfp.toml`, служба сверяет раскладку и читает прошивку
  `26 30`, `list`, `verify`, `unlock` отвечают, `enroll` открывает сенсор, снимает фон и ждёт палец опросом,
  закрытие клиента освобождает сенсор.

Что не проверено:
- касания настоящего пальца на Redox (регистрация и сравнение) — запусти `scripts/redox-hw.sh`;
- сборка рецептом внутри дерева Redox: проверена только команда, которую он выполняет
  (`redoxer install --path redox --root <stage>/usr --locked --no-track`);
- работа на железе без QEMU;
- обычный пользователь как клиент (тесты идут от root; смена пользователя проверена только для правила «писать может
  тот, кто открыл»).

Тесты схемы нельзя писать с запуском дочерних процессов: после `fork` в многопоточной программе поток, ждавший
результата, в Redox не просыпается. Сама служба и клиент дочерних процессов не запускают.

## Установка в образ Redox
Пока репозитории не опубликованы, рецепт берёт исходники из каталога рядом с собой:
```
recipes/other/elanfp/
  recipe.toml     копия dist/recipe.toml
  source/         этот репозиторий
  papilla/        репозиторий papilla
  drv-i18n/       репозиторий drv-i18n
```
В конфигурации образа:
```toml
[packages]
elanfp = "local"
```
Список схем, видимых обычному пользователю, задаётся по имени пользователя в `/etc/login_schemes.toml` и заменяет
список по умолчанию целиком: чтобы пользователь мог проверять свой палец, в его списке должна быть
`"fingerprint.elanfp"` вместе со всем, что ему нужно кроме неё. Пространство имён снимается при входе, поэтому схема,
зарегистрированная позже, видна только после повторного входа. В проверенной версии `userutils` список применяется
только к учётным записям с пустым паролем.

Воспроизводимость сборки: `xhcid_interface` закреплён на ревизии `base`, `redox-scheme` — только через `Cargo.lock`;
`papilla` и `drv-i18n` подключены путём, поэтому `--locked` перестаёт проходить, когда они меняются. Версия `xhcid` в
образе может отличаться от закреплённой — расхождение протокола проявится только при запуске.

## Отличия от Linux в защите
- TPM-драйвера в Redox нет: ключ лежит в файле `0600 root` на том же диске, что и шаблоны. От чтения другими
  пользователями он защищён правами, от снятого диска — только шифрованием RedoxFS. Привязка шаблона к пользователю,
  имени пальца и сенсору и проверка целостности работают так же.
- Входа по отпечатку в `login` и `sudo` Redox пока нет: есть служба и клиент.
- Служба работает от root (её запускает `xhcid`) и не сужает своё пространство имён.
- Привязки к встроенному порту нет: `xhcid` запускает службу для любого порта с этим идентификатором. Имя схемы одно,
  поэтому вторая служба не зарегистрируется, но первой может оказаться и внешнее устройство.
